## API-STABLE (W-065 / W-049, IHA-05, IHA-15): machine values of /api/v1 stay when display text changes

- Root cause: the STE pass renamed the detail keys in the rules; the Findings page printed `details[].key` as the row label,
  so the only way to change the label was to change the API value.
- Changed (`display.go`, `views.go`, `problems.html`): (a) contract C1: the map `detailLabels` gives the row label of a
  detail key: `Watch error`→`File watcher error`, `Failing items`→`Failed items`, `Items left`→`Remaining items`,
  `Bytes left`→`Remaining bytes`, `Type`→`Connection type`, `URL`→`API URL`, `Down since`→`Down from`,
  `First offered`→`Last request`; every other key (also the STE labels that the rules write today) shows as it is.
  Thus the map gives the same rows before and after fixer 3 restores the 78ef2d8 keys. The JSON keeps the raw key and value.
  (b) contract C6: `findings[].severity` stays `r.Severity.String()` (`ERROR`, `WARN`, `INFO`); the `counts` keys stay
  `error`, `warn`, `info`, `snoozed`, `urgent` (plus `ignored`, W-036). (c) `health_counts` next to the `health` line:
  `{"servers", "servers_up", "servers_disabled", "pcs", "pcs_online", "pcs_offline", "pcs_unknown"}` (C3, C4; see W-005 and W-003).
- User-visible: nothing on the dashboard changes for the keys of today. Integrations get `health_counts`.
- Tests: `TestAPIMachineValuesStay` (severity values, counts keys, raw detail key and UTC value in the JSON, label and
  local time on the page), `TestDetailLabels` (old and new keys), `TestAPICountsMatchOverview` (`health_counts` = the overview).
- DECISION: `health_counts.servers` is the number of entries in `servers[]` (disabled servers included), not only the
  enabled servers; `servers_disabled` counts the `disabled` entries. Thus `servers - servers_up - servers_disabled` is the
  number of enabled servers that are not up. `pcs_online` is added to the plan's example keys (the PCs tile shows it).
- DECISION: as the plan says, `findings[].severity` keeps the upper-case values of 78ef2d8; README and STYLE.md are the
  documents to correct (fixer 8, orchestrator).

## W-004 (medium): an unreachable or not-contacted server kept its last folder counts as healthy

- Root cause: the tile (`views.go`), the grid server cells (`serverCell`) and `/api/v1/status` counted folders with
  `Folder.FolderSync()`, which does not look at the server; only `Server.SyncStatus()` (HA) did.
- Changed: one helper, `folderStateKnown(sv)` = `sv.Status == up && sv.Loaded` (contract C5), and one counter,
  `countFolders(sv)`, used by the tile and the status API (`display.go`).
  - Tile (`overview.html`): when the state is not known, the folder line is grey, without icons:
    "5 folders · last known 2026-10-10 17:34: 5 idle" (the time is the last contact). A server that syncwatch never
    contacted shows "—". A server that is up and checked shows the line as before.
  - Grid (`views.go` `grid`, `grid.html`): the cells of such a server keep their text but get the grey `off` style, the
    icon ○ and the title "SOL unreachable, last known state 2026-10-10 17:34: Up to date" (or "not contacted",
    "certificate changed", "full check not complete"). A group with such rows says "○ N with an unknown state" and not
    "✔ no faults". A cell keeps its fault mark (a folder error before the server went down is still a fault, as the
    stale H4 finding is still open).
  - Status API: `servers[].folders.stale` (always present): `true` when the state is not known. The counts stay the
    last known counts (`idle` is not set to 0).
- User-visible: as above. HA (`/api/v1/ha`) is unchanged: it already gives `status: unknown` for such a server.
- Tests: `TestFolderStateAgreesEverywhere` and `TestAPICountsMatchOverview` are extended with a down and a not-contacted
  server; `TestStaleFolderState` (tile text, grid cells and summary, `folders.stale`, `uptime_s` null, back to normal
  after the server is up).
- DECISION: the time in "last known" is the full date and time (`2026-10-10 17:34`), the format of all other times on
  the dashboard. "17:34 today" is not used: a page that stays open after midnight keeps "today".

## W-011 (medium): the page kept "Real-time view" and old data when the live stream stopped

- Root cause: `app.js` had no handler for `htmx:sseError` / `htmx:sseOpen`, nothing fetched the sections again after a
  reconnect, and the 25 s keep-alive was an SSE comment (`: ping`) that never reaches JavaScript, so a silent drop was
  not visible either.
- Changed:
  - `server.go` `handleSSE`: the keep-alive is the event `event: ping` / `data: 1` (interval in `ssePing`, 25 s).
  - `app.js` (no inline script, CSP unchanged): on `htmx:sseError` a 30 s timer starts; if the stream does not open
    again in that time, the body gets the class `sw-offline` and the banner `#sw-conn` (`role="status"`) shows
    "✖ No connection to syncwatch from HH:MM. The page shows old data." (the time of the first error, in the configured
    time zone through `data-tz-offset` on `<body>`). On `htmx:sseOpen` after an error the state is cleared and
    `sse:update` is triggered one time on every `[hx-trigger~='sse:update']` element (the r0-k guard for forms in use
    still applies). A watchdog checks every 10 s: when no event (ping or update) came for 60 s while the page is
    visible, the page shows the banner and, if the stream is still "open", closes it and calls the sse extension's own
    error handler, which opens a new stream after 0.5 s and registers the sections on it again. When the page becomes
    visible after more than 60 s in the background, every section is fetched again.
  - `layout.html`: the banner element (class `conn-lost`, not `flash`: scripts that read the first `.flash` of a page
    must not find the hidden banner) and `data-tz-offset`; `overview.html`: "Real-time view" is in `span.live-on`, the
    other text "No connection to syncwatch" in `span.live-off`; `app.css`: `.sw-offline` hides "Real-time view", greys
    the health line and dims the tiles, the lists and the grid.
- User-visible: after 30 s without a stream (or 60 s without any event) the page says so; when the stream works again,
  the page shows the current data without a reload. A first page load does not fetch anything more than before (W-084).
- Tests: `TestEventStreamPing` (a ping event, no comment line, an update after a change), `TestConnectionLossShipped`
  (pins the script, the styles and the banner, and the time zone offset of Asia/Kolkata, 330). The browser behaviour
  itself is not a Go test; see the live check.
- DECISION: no server-side "update on connect" (the plan's optional part): the client fetches the sections after every
  reconnect that followed an error, and an update on each connect would cost one extra fetch of every section at each
  page load (W-084). The short gap between the page render and the first connect is unchanged.
- DECISION: the return from the background fetches the sections but does not clear the banner: only an open stream
  clears it (the stream can still be down at that moment).
