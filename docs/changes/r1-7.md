## 1. W-008: CLI `reset-admin-password` and `import-config` change a running syncwatch without a settings notice

**Root cause.** `configWatcher.check` (`internal/app/app.go`) only logged INFO "configuration reloaded…" and called
`ChannelsChanged`. `resetPassword` (`cmd/syncwatch/main.go`) wrote `auth.admin_hash` and deleted all sessions;
nothing in the server saw it. A second cause made the plan's literal fix send to the wrong channel: the command
writes the new webhook (`ImportSecrets`) into the database before the watcher sees the new revision, and
`notify.Notifier.NoticeLater` reads the webhook from the database when it is called. A capture in `check()`, also
before `holder.Set`, therefore captures the new webhook (checked: with that variant `TestCLIChangesAnnounced` fails
with "the import was announced to …/2/new, not to the webhook it replaced").

**What changed.**
- `internal/app/app.go`:
  - `ImportFile` words the change before it stores the secrets (`importChanges`: "The import changed these sections
    of Settings: …" and one line for each secret in the file, "The … is replaced." / "… is added."), and records it as
    a settings notice in the settings table (`cli.notice.<unix ns>-<random>`, JSON `{at, title, summary}`) **before**
    `saveConfig` changes the revision. `RecordPasswordReset` records the reset notice. One setting for each notice,
    thus two commands at the same time do not lose a notice.
  - `configWatcher` keeps the channels of the configuration that runs (`notice`, from `noticeLater` =
    `ntf.NoticeLater`), captured at start, after each save of this process, after each reload, and after a webhook
    change in Settings (the `ChannelsChanged` hook now also calls `watcher.channelsChanged`).
  - `check()` reads the revision first, then sends the recorded notices (`sendCLINotices`) to the captured channels,
    logs WARN `settings changed` `change=<title>` `detail=<summary>` `source="command line"` for each, deletes them,
    and then applies the new revision and captures the new channels. A notice older than 1 minute (a command while
    syncwatch did not run) gets "Changed at {time}." in the configured time zone.
- `internal/config/sections.go` (new): `ChangedSections(old, c)` gives the Settings sections that differ (Servers,
  Notifications, Checks, Structure rules and shares, Collector, Access), compared as YAML of the redacted parts
  (an empty and a missing list are the same; secrets never count).
- `internal/store/store.go`: `SettingsWithPrefix(prefix)`.
- `cmd/syncwatch/main.go`: `resetPassword` calls `app.RecordPasswordReset` after the sessions are deleted.

**User-visible change.** Discord gets "🔧 Administrator password changed with the command line" / "The new
administrator password is set. syncwatch logged out all sessions." and "🔧 Configuration changed with the command
line" / "syncwatch import-config replaced the configuration." + the changed sections + the secret lines, in less than
10 seconds, also during quiet hours (settings notice), to the webhook configured before the command. The log has a
WARN `settings changed … source="command line"` line. A command while syncwatch does not run is announced at the
next start, one time. CLI output is unchanged.

**DECISION (channel capture, differs from the plan text).** The channels are captured at the last apply and after a
webhook change in Settings, not in `check()` before `holder.Set`: the command has written the new webhook before
`check()` runs (see root cause). The command records the notice before it changes the revision, and `check()` reads
the revision first, thus the notice of an import is always sent with the channels of the configuration before it.

**DECISION (content).** The command, not the watcher, words the import notice: section labels of the Settings page
plus the secrets in the file (the dashboard import lists the same secret lines). The section-level diff is enough
(plan); `web.configChanges` is fixer 5's and stays where it is. An import that changes no section and brings no
secret sends no notice (as the dashboard import). Notices of the command line have no client address; the title
says "with the command line". The reset notice says "all sessions" (the command also logs out viewers; the form
logs out only the other administrator sessions).

**DECISION (next start).** A command run while no server runs is announced at the next start (plan: reset only;
here also the import, because the notice is recorded by the command). It goes to the channels configured at that
start: the old webhook is not known any more. No password check is added (plan.md section 4).

**Tests.** `internal/app/app_test.go` `TestCLIChangesAnnounced` (real notifier with a recording sender: one import
notice to the old webhook and a WARN line; one reset notice to the new webhook; no notice for an import without a
change; a notice recorded while no server ran is sent at the next start one time with "Changed at"; nothing left in
the store). `cmd/syncwatch/main_test.go` `TestResetPasswordRecordsNotice`. `internal/config/sections_test.go`
`TestChangedSections`. `internal/store/store_test.go` `TestSettingsWithPrefix`.
`TestConfigReloadedAfterExternalImport` is unchanged and passes.

**Live (s27).** Before: `w008-before.txt` (reset + import with a new webhook 999: 0 Discord messages, only the INFO
reload line). After: `w008-after.txt` (reset, then an import that replaces webhook 999 with 998: both notices

## 2. W-030 (key part): a new `secret.key` is made silently; `SYNCWATCH_SECRET_KEY` silently shadows `secret.key`

**Root cause.** `store.LoadKey` makes a new key when `secret.key` is missing and returns the environment key without
looking at the file (DD-6); nothing at start compares the key with the stored secrets, so the cause shows only later
as unreadable API keys and webhook.

**What changed.**
- `internal/store/secrets.go`: `UnreadableSecrets()` returns the names of the stored secrets that the key cannot
  decrypt (a nonce of the wrong size counts as unreadable instead of a panic in `gcm.Open`) and the number of stored
  secrets.
- `internal/app/app.go`: `Run` opens the store with `openServeStore`, which looks at `secret.key` before
  `OpenStore` and logs after it:
  - ERROR `cannot decrypt the stored secrets: restore the old secret.key` `cause="secret.key was missing, syncwatch
    made a new key"` `file=…` `secrets=<names>` when the key was just made and stored secrets exist (the plan's case);
  - ERROR `cannot decrypt the stored secrets: restore the old secret key` `key=<file or SYNCWATCH_SECRET_KEY>`
    `secrets=<names>` `stored=<n>` when the key is not the key of the secrets (a replaced file or a changed variable);
  - WARN `SYNCWATCH_SECRET_KEY is set, syncwatch does not use secret.key` `file=…` when both exist;
  - INFO `new secret key made` `file=…` for a new key without stored secrets (first start).

**User-visible change.** Log lines only. syncwatch still makes the new key and starts (no behaviour change); H1 and
the banner come as before. The notifier's own ERROR `cannot read the Discord webhook` now also appears once at start
(the watcher captures the channels then, item 1).

**DECISION.** Keep making the new key (plan). The check is "any stored secret that the key cannot decrypt", which
includes the plan's case (new key + rows) and also a replaced `secret.key` or a changed `SYNCWATCH_SECRET_KEY`
(worklist proposal). The maintenance commands are unchanged (they never make a key, r0-h).

**Tests.** `internal/store/store_test.go` `TestUnreadableSecrets`; `internal/app/app_test.go`
`TestSecretKeyProblemsLogged` (first start INFO; normal start logs nothing; missing key: ERROR with the cause and the
secret names, the new key exists; variable + file: WARN and ERROR `key=SYNCWATCH_SECRET_KEY`).

**Live (s27).** Before: `w030-before-volume.txt`, `w030-before-log.txt` (secret.key moved aside: H1 errors, no line
about the new key). After: `w030-after-replaced-key.txt` (the key that the base image made: ERROR with

## 3. W-042: `syncwatch probe` exits 0 when the connection fails, and loses the report when `--out` cannot be written

**Root cause.** `probe.Run` returned `write(…)` (nil) after "The connection failed" and the `config/folders`
failure; `write` returned the `MkdirAll` / `WriteFile` error without printing the report (firstuser F6).

**What changed (`internal/probe/probe.go`).** New `stop()`: writes the report as far as it got and returns
`errors.Join(reason, writeErr)`. Used after "The connection failed" (`the connection failed: …`), after the failed
`config/folders` request (`the request config/folders failed: …`) and after a refused event subscription (`the
subscription with the event mask failed: …`). `write()`: when `--out` cannot be made or written, the report goes to
standard output (`stdout`, a package variable for the test), then the error `cannot write the probe report to <file>
(syncwatch printed it to standard output): …`. `cmd/syncwatch/main.go` needs no change: `main` exits 1 on any error.

**User-visible change.** Exit status 1 and `syncwatch: the connection failed: …` instead of 0; the report is on
standard output when the file cannot be written. A complete run that writes its report still exits 0.

**DECISION.** Every early stop of the probe exits 1, also the refused event subscription (the plan named the
connection and `config/folders`): the report is then incomplete. Failures that the probe reports and continues after
(a browse, `/metrics`, the test long-poll, the event read loop) keep exit 0: they are results.

**Tests.** `internal/probe/probe_test.go` `TestProbeStopsWithAnError` (3 stops: error text and the report file),
`TestProbeReportKeptWhenOutCannotBeWritten` (the parent of `--out` is a file: report on standard output and the error,
for a stopped and a complete run; a writable `--out` gives no error and nothing on standard output).

**Live (s27).** `w042-after-wrong-key.txt` (fixed image, wrong gate token, default `--out` on the read-only root file
system: report on standard output, both errors, exit 1); `w042-probe-before-after.txt` (base image: exit 0 after "The
connection failed"; with `--read-only` the report is lost, `mkdir docs: read-only file system`; fixed image with the
right gate token and a writable `--out`: exit 0).

**README (fixer 8), STE-checked.** Server probe section (README.md:394-404): before the command, "The image runs as
user 65532. Make the directory of the report writable for this user first: `mkdir -p docs && sudo chown 65532 docs`."
After the list: "The probe exits with status 1 when it cannot test the server. The causes are a failed connection, a
