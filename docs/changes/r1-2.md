## 1. W-001: a graceful Syncthing stop resolves open folder findings

**Root cause.** `internal/collector/events.go` cleared `Folder.Error` on `StateChanged` from `error` to any other state. A Syncthing that stops gracefully (SIGTERM, `docker stop`, a NAS app stop) sends exactly that event for each folder in error, 1 to 3 ms before its API closes. Checked with a native Syncthing 2.1.5 (`native\exp1-marker-break-result.txt`, `exp1-path-break-result.txt`): Ctrl-Break gives `StateChanged {from: error, to: idle}`, then the long-poll breaks; `db/status` never answered "idle" in that window. A stop through `POST /rest/system/shutdown` sends no such event (`exp1-marker-api-result.txt`). After the first failed long-poll the server still counts as up (`down_after_failures` 2), thus the next evaluation resolved H4, the notifier sent "Resolved" after min(debounce, 5 minutes), and H4 opened again with a second urgent message when Syncthing started again (the record had `ResolvedNotifiedAt`, thus `PingedAt` was not carried over).

**What changed.**

- `events.go`, `apply`: `StateChanged` from `error` to another state still sets `State`, but a folder with an error keeps `Error` and is noted in `c.clearDue` (folder ID, time of arrival). A `FolderSummary` that says "no error" for a folder with an error does the same (it carries the same data as `db/status`). A later `StateChanged` to `error`, or a `FolderSummary` with an error, removes the note.
- `events.go`, new: `clearConfirm` (10 s, a variable for tests), `noteClear`, `confirmClears`, `clearWait`, `dropClears`.
- `collector.go`, `eventLoop`: after each long-poll that Syncthing answers (empty or with events, after `applyBatch`), `confirmClears` clears the errors noted at least 10 s before that answer. While a clear waits, the long-poll timeout is shortened to the moment it can be confirmed (whole seconds, at least 1 s; `clearWait`), thus a repair is confirmed after about 10 to 11 s, not after a full `event_timeout`. No extra request.
- `collector.go`, `Run`: when the session ends, `dropClears` forgets the waiting clears (the folders keep their errors) and sets `needFull`, thus the next session starts with a full check that reads the folders again, also when Syncthing did not restart. `fullCheck` resets `clearDue` (every folder was read again). The comment of `needFull` says this.

**User-visible.** When Syncthing on a server stops, the folder findings of that server no longer resolve: no false "✅ Resolved" and no second urgent message after the restart. H4 stays open, becomes `stale` while the server is down and continues as the same finding after the restart. A folder that is really repaired while Syncthing runs loses its error about 10 to 11 s after the event (before: at once); its resolved message comes after the usual wait. The dashboard shows the state that the event reported (for example `idle`) with the error during those seconds; the folder counts as an error folder until then.

**Tests** (`internal/collector/events_test.go`):

- `TestFolderErrorKeptWhenSyncthingStops`: a fake Syncthing with a broken folder sends `StateChanged {error → idle}` and `ListenAddressesChanged`, then answers only 502 (like the gate while Syncthing does not run), then starts again with a new `startTime`. A real `engine.Engine` evaluates at each step: H4 stays open with the same ID after the first failure (server still up), is stale while the server is down, and is the same record after the restart (same `OpenedAt`, same `PingedAt`, not stale); no resolved message is due; the history has 1 open occurrence.
- `TestFolderRepairClearsAfterConfirmation`: repairs by `StateChanged` and by `FolderSummary` keep the error for at least `clearConfirm` and clear it within one long-poll after that; an error that comes back in the meantime stays.
- `TestUnconfirmedRepairReadAgain`: the session breaks before the confirmation; the folder keeps its error, the reconnect (no Syncthing restart) runs a full check and reads the folder again.
- `TestClearWait`: the shortened long-poll timeout.

On the base code (`unit-before.txt`): `TestFolderErrorKeptWhenSyncthingStops` fails ("p-beta lost its error at the stop", and with that line as a log: "H4 resolved when Syncthing stopped"), `TestUnconfirmedRepairReadAgain` fails ("the error was cleared at once"). The other two use new symbols.

**Live (kit s22, `live-w001-*`).** `envctl inject s22 folder-error SOL live-fjord-1source`, the urgent message, `docker stop sw-s22-sol`, 75 s, `docker start sw-s22-sol`.

- Before (r0 image, `live-w001-before\`): log "finding resolved H4" 1 s after `docker stop`; Discord #4 "✅ Resolved: Folder sync stopped: LIVE-FJORD-1SOURCE on SOL" 37 s after the stop, #5 "🚨 Server unreachable: SOL", #6 a second "🚨 Folder sync stopped: LIVE-FJORD-1SOURCE on SOL" with the role mention after the start (H4 opened again with a new `opened_at`). `envctl heal`: H4 gone 2 s later.
- After (`fix-r1-2` at `a397e3a`, `live-w001-after\`): H4 stays open with the same ID and `opened_at`, is `stale` from 15 s after the stop until the full check after the start; Discord has only #10 "🚨 Server unreachable: SOL" and #11 "✅ Resolved: Server unreachable: SOL" (no H4 message). `envctl heal`: H4 gone 12 s later (the confirmation).

DECISION: the confirmation is a long-poll that Syncthing answers at least 10 s after the event. There is no `db/status` read for it (an immediate read during a stop is not trusted, and a later read is an extra request per folder); the long-poll timeout is shortened instead. A really repaired folder resolves about 10 s later than before (at most one long-poll later); the resolved message waits min(debounce, 5 minutes) anyway.

DECISION: a `FolderSummary` without an error waits in the same way as `StateChanged`. No evidence shows a `FolderSummary` during a stop, but it carries the same data as `db/status`, which the plan says not to trust during a stop.

DECISION: when the session ends with waiting clears, the next session starts with a full check (one more full check, only in that case). Without it, a short network break right after a real repair kept the old error until the next periodic full check (4 hours by default).

DECISION: the optional part (apply `DeviceDisconnected` only after the same confirmation, against the H11 resolve-and-open at each Syncthing restart) is not done; see "Not done".

## 2. W-012: H10 misses conflicts whose copy a PC makes

**Root cause.** H10 counts only the increase of each server's own `/metrics` counter `syncthing_model_folder_conflicts_total` (`readConflicts`, `RecordConflicts`, `ConflictsSince`). Syncthing raises it only on the device that makes the conflict copy. In hub and spoke a NAS makes the copy only when it applied the losing version first. The copy reaches the NAS as an ordinary file: a `RemoteChangeDetected` event with its path, which `diskChange` dropped (directories only).

Checked with a native Syncthing 2.1.5, PC1 – NAS – PC2 (`native\exp3-result.txt`):

- A PC makes the copy (PC1 paused with an older edit, PC2 saves later, PC1 resumes): the NAS gets `RemoteChangeDetected {type: file, action: modified, path: docs\notes.sync-conflict-20261011-003353-ISJJGP4.md}`; counters NAS 0, PC1 1.
- The NAS makes the copy (its own older edit loses): the NAS reports its copy as `LocalChangeDetected` (not `RemoteChangeDetected`); its counter is 1. Thus counting only `RemoteChangeDetected` counts no copy twice.
- The action of a new copy is `modified`, not `added` (Syncthing uses `added` only for a version vector with one counter of value 1). The path uses the separator of the server (`\` on Windows).
- In the second case a PC that held the losing version also made a copy, which reached the NAS as `RemoteChangeDetected`: the NAS has 2 new copies, counted 1 by `/metrics` and 1 by the event.

`RemoteChangeDetected` is in `stclient.EventMask` (`client.go:79`), and the gate builds its fixed mask from `stclient.EventMask` (`gate.go:87-93`). Nothing to change there.

**What changed.**

- `internal/store/conflictevents.go` (new, contract C8): `func (s *Store) AddConflicts(server, folder string, n int64, at time.Time) error` inserts a row into the existing `conflict_deltas` table (no schema change; `n <= 0` writes nothing). `ConflictsSince` counts these rows with the counter increases; `PruneConflicts` removes them after 60 days, as before.
- `events.go`: in the `LocalChangeDetected` / `RemoteChangeDetected` case, before `diskChange`, `conflictCopy` counts a `RemoteChangeDetected` of type `file`, action not `deleted`, whose base name (after the last `/` or `\`) matches `\.sync-conflict-\d{8}-\d{6}-[A-Z0-9]{7}`: one conflict for (this server, folder), at syncwatch's time. A bounded set (`copySet`, 1,000 keys of folder and path, the oldest forgotten first) counts each copy once, also when it changes again. An INFO log line `conflict copy received` (folder, path) shows each counted copy; a store error logs WARN `cannot save the sync conflict`.
- `collector.go`: the field `copies`.

**User-visible.** In events mode H10 opens on each NAS that a conflict copy reaches, within seconds (the next evaluation), also when a PC made the copy: in the kit both AKKA and SOL get H10 for one conflict between 2 PCs. The H10 text and rule are unchanged ("{count} new sync conflicts in folder … in the last 7 days"); the count is now the number of new conflict copies that the server made or received. Polled mode sees only the copies that the server made (the counter), as before.

**Tests.**

- `internal/store/conflictevents_test.go`, `TestAddConflicts`: rows from `AddConflicts` and counter increases add up in `ConflictsSince`; `n = 0` writes nothing; the window and `PruneConflicts` apply.
- `events_test.go`, `TestConflictCopiesFromEvents`: `RemoteChangeDetected` for `docs/notes.sync-conflict-20261010-205040-OHP4C7G.md` counts 1; the same event again counts nothing; a Windows path without extension counts 1; a deleted copy, a normal file, a directory with a conflict name, a file inside such a directory and a `LocalChangeDetected` copy count nothing (total 2). Fails on the base code (`unit-before.txt`: no conflicts).
- `TestCopySetBounded`: the set keeps 1,000 keys and forgets the oldest first.

**Live (kit s22, `live-w012-*`, ESP-03 with the kit's Docker PCs).** RENDER-01 pauses `live-fjord-2projectfiles` and appends to `docs/notes.md` (mtime 60 s older), WS-ANNA appends later, RENDER-01 resumes and makes the copy.

- Before (r0 image, `live-w012-before\`): `notes.sync-conflict-20261011-005956-HYRAF3O.md` reaches AKKA and SOL within 3 s; counters AKKA 0, SOL 0, RENDER-01 1; no H10 after 64 s.
- After (`fix-r1-2`, `live-w012-after\`): the next copy (`…-010603-HYRAF3O.md`) reaches both NAS; counters AKKA 0, SOL 0, RENDER-01 2; log "conflict copy received" on AKKA and SOL, H10 "1 new sync conflict in folder LIVE-FJORD-2PROJECTFILES on AKKA" and the same on SOL 2 and 3 s after the copy was made. After a restart of the syncwatch container both H10 still say 1 (`after-syncwatch-restart.txt`).

DECISION: count only `RemoteChangeDetected` (a copy that the server makes comes as `LocalChangeDetected` and is in its counter). Copies that reach a server after a conflict on another server count on that server too, thus one conflict can show as H10 on both NAS. That is correct for "new conflict copies in this folder on this server".

DECISION: the time of the row is syncwatch's clock (as `RecordConflicts`), not the event time of the NAS.

DECISION: the set of counted copies is in memory. After a syncwatch restart it is empty, but the first session starts with a full check and does not apply the events that Syncthing buffered before; thus no copy counts twice. Copies that arrive while syncwatch is down, during a gap in the event IDs or between the start of a session and its full check are not counted (the server's own copies still are, by the counter).
