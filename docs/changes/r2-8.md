## 2. W-034 (lead): X-Forwarded-Proto only from trusted proxies

**Before.** `secureCookies` believed `X-Forwarded-Proto: https` from any client (DW-11).

**Changed (`auth.go`, `main.go`, `app.go`).** `requestScheme(r)`: `https` for a request over TLS, or from an address of the
trusted proxies with `X-Forwarded-Proto: https`; else `http`. The last value of the header counts (a proxy that adds its
value keeps the value of the client before it: `https, http` is http). `fromTrustedProxy` compares the client address
(IPv4 in IPv6 form as IPv4, no zone) with the prefixes. `secureCookies` and the scheme rule of W-027 use it.
`TrustProxies` stores the prefixes masked and in IPv4 form. `main.go` reads `SYNCWATCH_TRUSTED_PROXIES`
(comma-separated IP addresses or CIDR prefixes; an address is its single-address prefix; a zone, a port or a name is
refused: `SYNCWATCH_TRUSTED_PROXIES: "proxy.lan" is not an IP address or a CIDR prefix. Use for example 172.18.0.2 or
172.18.0.0/16.`). `Run` calls `TrustProxies`.

**What the user sees.** Nothing changes for a dashboard on HTTPS or on plain HTTP. Behind a TLS reverse proxy without
`SYNCWATCH_TRUSTED_PROXIES`, the cookies lose the Secure flag (the forms keep working); with it, the cookies are Secure
with the `__Host-` names (W-027).

**Tests.** `TestForwardedProtoOnlyFromTrustedProxies` (no Secure from an address that is not trusted, also with a list
of other addresses; the login works; Secure from `127.0.0.1/32`; `http`, empty, `HTTPS`, `https, http`, `http,https`;
clients and prefixes in IPv6 form), `TestEnvTrustedProxies`, the case in `TestServeRefusesBadEnvironment`.

**Live (`live-w034-proxy.txt`).** Native, plain HTTP: without the variable, `X-Forwarded-Proto: https` gives
`sw_csrf … HttpOnly; SameSite=Lax` (no Secure). With `SYNCWATCH_TRUSTED_PROXIES=127.0.0.1` (start log
`trusted_proxies=127.0.0.1/32`): `__Host-sw_csrf … Secure`; `http` and `https, http` give the plain cookie; a login with
`Origin: http://…` through the trusted proxy is refused (403), with `Origin: https://…` it works (303, `__Host-` cookies).

## 3. W-027 (lead): CSRF Origin rules, a CSRF token of the session, `__Host-` cookie names

**Before.** `checkCSRF` accepted `Origin: null` and an `http` Origin on HTTPS; the CSRF token was not bound to the session
and did not change at the login (`sessions.csrf` was always empty); no `__Host-` prefix (R1-SEC-04).

**Changed (`auth.go`).**
- `requestInfo` has `HTTPS bool` (from `requestScheme`, set by `resolve`). `checkCSRF(r, info)` keeps its signature (C10).
- Origin (`sameOrigin`): refused when it is `null`, not `http`/`https`, has a user, a path, a query or a fragment, or another
  host and port than the request (without regard to case; before: a suffix compare); an `http` Origin is refused when
  the browser uses HTTPS. Behind a proxy that is not trusted (`http`), both schemes of the host pass, as before.
- `startSession` (login, first start, password change) makes a new CSRF token, stores it in `sessions.csrf` and sets the
  CSRF cookie to it. `resolve` uses the token of the session when it has one (a cookie that another page set does not
  replace it); a session with an empty token (older version) uses the cookie, as before. The forms get the token of
  the session (`info.CSRF`).
- Over HTTPS the cookies are `__Host-sw_session` and `__Host-sw_csrf` (Secure, Path `/`, no Domain), and only these names
  are read. Over HTTP the plain names, without Secure. The login over HTTPS also clears the plain names. The logout
  deletes the sessions of both names and clears the session and CSRF cookies in both forms (over HTTP only the plain
  names: a browser refuses a `__Host-` cookie without HTTPS).

**What the user sees.** Over HTTPS each person logs in one time after the update. A tab that was open before a login or a
password change needs a reload before its next form ("CSRF token missing or not valid: reload the page and try again").

**Tests.** `TestHostCookiesOverHTTPS` (`httptest.NewTLSServer`: the attributes, the new CSRF cookie at the login and in the
session, the plain names cleared, a plain session cookie of an older version is not read, the logout clears 4 cookies
and ends the session), `TestPlainCookiesOverHTTP`, `TestCSRFOriginRules` (plain HTTP: no Origin, both schemes of the
host pass; null, another host, a path, `ftp`, a user refused. HTTPS: null and `http://` refused. A trusted TLS proxy:
`http://` refused), `TestCSRFTokenBoundToSession` (the anonymous pair with an administrator session → 403; a session
without a token uses the cookie), `TestCSRFTokenChangesAtLogin`. Changed: `TestSecureCookiesOverHTTPS` (the
`__Host-` name), `TestViewerLoginKeepsAdminFailures` and `TestCookiesAreSameSiteLax` (they read the token again after
the login).

**Live (s28, `t_cookies_csrf_r2.py`, the r1 script with the port, the password and the new names;
`live-w027-cookies-csrf.txt`).** Before (r1 evidence `dw08-dw12-cookies-csrf-headers.txt`): Origin null 303, scheme
downgrade 303, anonymous pair 303, "csrf cookie rotated at login: False". After: `__Host-sw_csrf` and `__Host-sw_session`
(Secure, HttpOnly, SameSite=Lax, Path `/`); "csrf cookie changed at login: True"; the form token is the new cookie;
Origin null 403, `http://` downgrade 403, `https://` same host 303, another host 403, no token 403, the anonymous pair
403; the session under the plain name `sw_session` → 303 to the login; the logout clears `sw_session`, `sw_csrf`,
`__Host-sw_session`, `__Host-sw_csrf`; `GET /logout` 405. Chromium (`ui/shot`, `live-w027-browser\`): login, Settings →
"Send test message" (a form with Origin) → "syncwatch sent the test message …", log out → `/login`; no console errors.

**DECISION (plan).** Over HTTPS each session from before the update ends (new cookie names): one login after the update
(Docs stage, "What you must do").

**DECISION.** The logout also clears the CSRF cookie: the next page gets a new anonymous token, not the token of the old
session.

## README lines (Docs stage)

STE-checked (`ste-readme-mapping.md`, 39 sentences, 100 percent). Places are suggestions.

**Health check** (with "Where to run syncwatch" and the outside check):
- `/healthz` answers `ok` (HTTP 200) when syncwatch is healthy.
- It answers HTTP 503 with one line for each reason, from this list:
  - The database does not answer.
  - syncwatch did not evaluate the checks for more than 5 minutes.
  - Notifications fail for more than 15 minutes (`SYNCWATCH_HEALTH_NOTIFY_LIMIT`).
- syncwatch finds a notification failure only when it tries to send a notification.
- The answer contains no error text of Discord, because `/healthz` needs no login.
- The healthcheck of the image uses `/healthz`. Docker then marks the container as unhealthy.
- `docker inspect syncwatch` shows the reason, for example `the health check returned HTTP 503: notifications fail from 2026-10-11 21:04`.

**Environment variables** (table rows):
- `SYNCWATCH_HEALTH_NOTIFY_LIMIT`: how long notifications can fail before `/healthz` answers 503. A duration from 1 minute to 1 day, default `15m`.
- `SYNCWATCH_DEADMAN_URL`: the URL of an outside monitor service that syncwatch calls. Empty: off.
- `SYNCWATCH_TRUSTED_PROXIES`: the IP addresses or CIDR prefixes of your reverse proxy, comma-separated. Empty: syncwatch ignores `X-Forwarded-Proto`.
- syncwatch does not start when one of these values is not valid. The log names the variable.

**Dead-man URL** (new paragraph):
- Set `SYNCWATCH_DEADMAN_URL` to the URL of an outside monitor service, for example healthchecks.io or Uptime Kuma (push monitor).
- After its checks, syncwatch sends `GET` to the URL at most every 30 seconds, while `/healthz` answers `ok`.
- When the calls stop, the service sends its own alarm. This also works when syncwatch stops, when the host is off, or when Discord refuses the messages.
- Set the grace time of the service to 5 minutes or more.
- syncwatch waits at most 10 seconds for an answer and does not follow a redirect.
- The log names only the host of the URL, because the path can contain the secret of the service.

**Time when syncwatch did not run** (Notifications):
- syncwatch records a heartbeat in the database every 30 seconds and when it stops.
- When syncwatch starts more than 2 minutes after the last heartbeat, the log has the line `syncwatch did not run` with the times. The next notification also gives the times, for example "syncwatch did not run from 21:04 to 21:24."
- After a crash, the time starts at the last heartbeat, at most 30 seconds before the crash.

**Behind a reverse proxy:**
- Set `SYNCWATCH_TRUSTED_PROXIES` to the address of the reverse proxy, for example `172.18.0.2` or `172.18.0.0/16`.
- syncwatch then accepts `X-Forwarded-Proto: https` from the proxy, and the cookies get the Secure flag and the `__Host-` names.
- syncwatch ignores the header from all other addresses. Without the variable the login works, but the cookies have no Secure flag.

**Security** (Forms, Cookies):
- Each form sends a CSRF token. The token belongs to the session, and syncwatch makes a new token at each login.
- syncwatch refuses a form from another page: another host name, `Origin: null`, or an `http://` page when the dashboard uses HTTPS.
- Over HTTPS the cookies are `__Host-sw_session` and `__Host-sw_csrf`: Secure, path `/`, no domain. A page on another host name cannot set or replace them.

**Pinned certificates** (Security, Keys stay with their server):
- When the collector pins a certificate without an administrator, syncwatch sends a settings notice with the URL and the short fingerprint.
- This happens at the first contact with a server and after a change of the API URL.
- It also happens when a CA-signed certificate replaces the pinned certificate for the same host name.
- Compare the fingerprint with the certificate of the server. If they are not the same, remove the pinned certificate in Settings → Servers.

**Command line** (Lost administrator password; Bootstrap file, Later changes):
- syncwatch keeps the settings notices of `reset-admin-password` and `import-config` until Discord accepts them. (With fixer 4's W-051.)
- `import-config` gives the servers that the file removes, for example "The import removed the servers AKKA, SOL and deleted their API keys and pinned certificates."
- The command does not ask you again before the import, because a person who can run the command can also change the database.
- Export the configuration before an import.
