## 1. W-046 (lead): one finding for one cause

**Root cause.** `overlaps` reported every Syncthing folder inside another as an urgent S1, also when the outer folder was a
share root (S2); a full database disk is a folder error of every folder, and each gave its own urgent H4; a pull refused for
lack of space in a folder is a failed item, which waits for `failing_files`.

**What changed.**
- `structure.go`: `structure()` computes the share-root folders first (`shareRootFolders`, the S2 condition) and gives the set
  to `overlaps` and `shareRoots`. `overlaps` makes no S1 when the outer folder is a share-root folder. The S2 finding has one row
  `Syncthing folder inside` (`<folder ID> — <path>`) for each Syncthing folder inside it (at most 20, then `More folders inside`
  with the number of the others), and the message gives the count: "Share root AKKA-LIVE-4FINALS on AKKA is a Syncthing folder
  (AKKA-LIVE-4FINALS). It contains 2 other Syncthing folders. Sync each project folder as a separate Syncthing folder".
- `health.go`: `databaseDisk` makes 1 H4 for each server (ID key `database-disk`, subject "Syncthing database on SOL") when
  1 or more folders have an error that contains "insufficient space on disk for database" (any case): "Syncthing on SOL stopped
  5 folders: the disk of its database is full (<error>)"; `Since` = the earliest `StateChanged` of the stopped folders in state
  error; rows `Error`, `Stopped folders` (labels, at most 20, then "…and N more"), `Folder IDs`. ERROR and urgent (catalog).
  `folderHealth` gives these folders no reason "out of space" or "folder error" for this error, and no H5.
- `health.go`: a failed item (`FileErrors[i].Error`) with "insufficient space", "no space left" or "free space" adds the reason
  "out of space": with 2 reasons H4 opens at once, not after `failing_files`.

**DECISION (orchestrator, recorded here):** a pull that Syncthing refuses for lack of space in a folder opens H4 at once. To
undo: remove the loop over `f.FileErrors` that sets `space` in `folderHealth`.
**DECISION W-046-1:** the S2 rule needs S2 to be enabled. With S2 disabled in Settings → Checks, `shareRootFolders` is empty and
the folders inside a share-root folder get S1 as before (else no finding would report them).
**DECISION W-046-2:** only the outer folder decides. A folder inside a project folder that is itself inside the share-root
folder keeps its S1 with the project folder. 2 folders at the same path keep their S1 "same path", also at a share root.
**DECISION W-046-3:** `Folder IDs` lists every stopped folder (the limit of 20 is for the labels only); the message and `Error`
use the error of the first stopped folder by name (the folders have the same text, only the percentage can differ).
**DECISION W-046-4:** a folder with the database error and another reason (failed items, a watcher error with no space) gets
its own H4 for the other reasons; its `Since` is not the time of its error state (that state belongs to the database error).

**User-visible.** 1 urgent finding and 1 line in the urgent and in the resolved message for a share root added as a Syncthing
folder and for a full database disk; the dashboard counts 1 finding. A full folder disk gives H4 "out of space" at once.

**Tests.** `TestShareRootListsTheFoldersInside` (3 folders inside → 1 S2 with 3 rows and the count, no S1, the S1 of 2 other

## 3. W-057.texts: links between servers and sites; messages that name the sites

**What changed.**
- `model/links.go`: `(*Snapshot).ServerLinks()` (contract C3): the pairs that H2 checks (2 polled servers with both device IDs
  that have each other configured as devices), A before B in configuration order. Connected when one side has a connection to
  the other while both are up and loaded (`Since` = the earlier `StartedAt` of the connected sides; zero when not known);
  disconnected when both are up and loaded and not connected (`Since` = the later of the 2 last-seen times); unreachable when a
  server of the pair is not up or not loaded (`Since` zero). `SiteLinks(links, siteOf, serverOrder)`: 1 site link for each pair
  of different sites that has 1 or more server links; links of servers without a site and links inside 1 site are not included;
  A before B in the order of their first server in `serverOrder`; connected when 1 link is connected (`Since` = the earliest
  `Since` of the connected links), else unreachable when 1 is unreachable (`Since` zero), else disconnected (`Since` = the latest
  `Since`); `Servers` lists the server pairs. `nil` when there is no site link.
- `engine.go` `Evaluate`: `snap.Links = snap.ServerLinks()` and `snap.SiteLinks = model.SiteLinks(snap.Links, cfg.SiteOf,
  <IDs of cfg.Servers>)` before the rules run and before the view is published; `visibleFingerprint` includes both (a reconnect
  between 2 evaluations changes "connected from 08:12" only).
- `health.go` H1 (network failures, `networkFailure`): with `cfg.Site` and the server's site set and different, "Server SOL
  (Branch office) is unreachable from IVAR Office: <error>" and `Possible causes` "The VPN between IVAR Office and Branch office
  is down, or the server is off or does not answer."; else the texts of r1. A row `What AKKA sees` for each other polled server
  that is up and has a connection to this server: "AKKA is connected to SOL. Thus Syncthing on SOL runs, and the network path
  from syncwatch to SOL is down." (see DECISION W-057-3).
- `health.go` H2: `What to check` "The VPN between IVAR Office and Branch office, and Syncthing on both servers." when the 2
  servers have different sites; else the text of r1.

**DECISION W-057-1:** the site texts of H1 only for a network failure (the plan's heading): a refused API key, a TLS or a
configuration error keeps the r1 texts. The same site for syncwatch and the server, or a missing site, keeps the r1 texts.
**DECISION W-057-2:** a pair without both device IDs or without the device configured on both sides is no link (the pairs of
H2). A server that has the other paused gives a disconnected link (H2 skips it, H6 reports the pause). The order of the sites
follows `cfg.Servers` with the disabled servers (a disabled server is not in `Links`).
**DECISION W-057-3 (found live):** the row `What AKKA sees` also needs 10 minutes without contact between syncwatch and the
server (`deadLinkTime`). During a silent cut of the VPN on s22, AKKA's Syncthing kept its connection to SOL for 5 minutes 44
seconds in one run and for 7 minutes 12 to 32 seconds in a second run (Syncthing closes a connection that receives nothing
after approximately 5 minutes; the kit measured 300 to 421 seconds before), and the row said "AKKA is connected to SOL. Thus
Syncthing on SOL runs" for a dead connection (`live\73-h1-row-poll.txt`, `live\94-h1-row-poll-fixed.txt`). After 10 minutes
a connection that AKKA still reports is real. The row is also only for a network failure: for a refused API key it would be
wrong.

**User-visible.** With sites: "Server SOL (Branch office) is unreachable from IVAR Office: timeout" and the VPN between the 2
sites as the possible cause (also as the advice line of the urgent message, fixer 4); H2 names the 2 sites. Fixers 5, 6 and 7

**Tests.** `TestServerLinks` (connected from the earlier start of the 2 sides; unreachable when a server is down or not loaded;

## 5. W-059 (lead): H5 shows the progress of a slow sync

**What changed.** `progress.go` and `health.go` (H5 for a folder and for a device): the time rule (`stuck_sync`) stays. New rows
after the rows of 78ef2d8: `Received` ("1.6 of 2.1 GB": folder view `GlobalBytes − NeedBytes` of the folder; device view of the
completion; only when the size is known), `Speed` (from `sv.Progress[folder][device or ""]`, fixer 3: the decrease of
`NeedBytes` per second between the newest point and the newest sample at least 10 minutes older; "0 (no data arrived in the
last 10 minutes)" when it did not decrease; no row when the samples do not go back 10 minutes), `Time left` ("approximately 4
minutes", the need now divided by the speed; no row when the speed is 0 or not known). The folder message adds ", 1.6 of 2.1 GB
received, approximately 4 minutes remaining"; the device message adds ", approximately 33 hours remaining". Sizes have 2
significant digits (`sig2`), the time left whole minutes (less than 2 hours), hours (less than 2 days) or days, thus 2
evaluations 30 seconds apart give the same message. `Items left` and `Bytes left` stay.

**DECISION W-059-1:** the newest point for the speed is the need now when the newest sample is 1 minute or more old. Syncthing
sends no progress while a sync waits, and without this the speed of the 10 minutes before a stall stayed until the next full
check ("Time left: approximately 4 minutes" for a sync that stopped).
**DECISION W-059-2:** no `Speed` and no `Time left` for a held H5 (the device is away and receives nothing); `Received` is from
its last completion.
**DECISION W-059-3 (STE):** the device message adds only the time left: with the sizes it had 27 words (limit 25); its
percentage is in the message, the sizes are in the row `Received` (commit `eb92dc8`).
**DECISION W-059-4:** decimal units (1 GB = 1,000,000,000 bytes, as the decision card's "2.15 GB" for 2 GiB); MB below 1 GB, also
for small speeds ("0.016 MB each second"): GB and MB are the abbreviations of the glossary. "less than 1 minute" below 30
seconds.

**User-visible.** "Folder LIVE-NORRSKEN-2PROJECTFILES on AKKA did not finish the sync in 24 hours (syncing, 1 remaining item, 1.6
of 2.1 GB received, approximately 4 minutes remaining)" and the rows Received, Speed "2.4 MB each second", Time left.

**Tests.** `TestStuckSyncShowsProgress` (samples that drop 2.4 MB each second → the message, Speed "2.4 MB each second", Time left
"approximately 4 minutes", Received "1.6 of 2.1 GB", the time rule and the machine values stay; 30 seconds later with 72 MB more
→ the same message and rows; the device view → "160 of 220 GB", "0.5 MB each second", "approximately 33 hours"; held → no speed;
