## 1. W-053 (lead) and W-031: named API tokens with a scope and a last use

- **Store** (`store/tokens.go`): new `(*Store).APITokenByName(name)` (without regard to case, as the name rule; nil when
  no API token has the name). The rest is the foundation's API.
- **Import** (`settings.ImportSecrets`): `api.token` no longer writes the secret `api.token`. It is the new value of the
  API token named "API token" (`store.LegacyTokenName`; its scope stays), or syncwatch adds that API token with the scope
  full. The checks run before a secret of the file is stored: with 5 API tokens and none named "API token" the import is
  refused with "There are 5 API tokens. syncwatch cannot add the API token of the file (api.token). Revoke an API token
  first."; the value of another API token is refused with "The API token of the file (api.token) has the value of the API
  token "Scripts". Use a different value." (a SQL UNIQUE error before). The value of "API token" itself changes nothing.
  The API token counts as 1 secret, as before (the bootstrap scrub still removes it). `NeedKey`, `SetServerKey`,
  `DropRemovedServers` do not change.
- **Auth** (`api.go` `apiAuthorized(w, r, need)` → `(apiCaller, bool)`): the bearer value is looked up with
  `APITokenByValue` (hash; the old secret path and the foundation's fallback are gone). `need` is `store.ScopeFull` for
  `/api/v1/status` and `store.ScopeHA` for `/api/v1/ha`; an ha API token on `/api/v1/status` gets
  `403 {"error":"the API token permits only /api/v1/ha"}` with `WWW-Authenticate: Bearer realm="syncwatch",
  error="insufficient_scope", scope="full"`. An unknown value: 401 `invalid token` and the once-a-minute log line as before.
  A database error: 500 `internal error` and an ERROR log line.
- **Last use** (`tokens.go` `touchAPIToken`): `TouchAPIToken` when the last use in the row that the request read is more
  than 1 minute old (or zero, or in the future). Thus at most 1 write a minute for each API token, and the time on the page
  is at most 1 minute late. A request that the scope refuses (403) is also a use. A failed write: one WARN line a minute
  for each API token ("cannot record the use of the API token").
- **Settings → API** (`settings_api.html`, `tokens.go`): a list item for each API token (name; Scope "Home Assistant:
  /api/v1/ha only" or "Full: /api/v1/status and /api/v1/ha"; Made; Last used, or "never") with "Replace" and "Revoke".
  Each asks first: "Replace the API token "Home Assistant"? The programs with this API token lose access immediately."
  (the same with Revoke). "Add API token" (name, at most 40 characters; scope, Home Assistant selected) while fewer than 5
  exist; else "There are 5 API tokens. Revoke an API token before you add an API token.". The value of a new or replaced
  API token shows one time in the "New API token" panel at the top of the answer: "Copy the value of the API token "…"
  now. syncwatch does not show it again." and the `Authorization: Bearer` line with `GET /api/v1/ha` only (scope ha) or
  both addresses (full). r1's text about the answer (W-032) stays; a second paragraph says what the scope Home Assistant
  reads. A refused form (a name in use, more than 5, an unknown ID, an unknown op) answers the Settings page with 422 and
  the reason above the list (`#api-error`, focused, as the forms of r1), the typed name and scope stay.
  `POST /settings/api-tokens` takes `op` = `add` (`name`, `scope`), `replace` (`id`), `revoke` (`id`), `revoke-old`.
- **API token of an older version**: when the secret `api.token` is still stored (the store cannot decrypt it, or a
  downgrade made it after the move), the card says "The database has an API token of an older version. syncwatch cannot
  decrypt it. Revoke it." (or "… syncwatch does not accept it. Revoke it." when it decrypts) with the button "Revoke old API

## Changes to /api/v1 (for the changelog "Integrations" and the README field reference)

Changes of the third round (r2), for `docs/CHANGES-review.md` after item 17:

18. **Access (W-048).** Without an API token, only a logged-in session (administrator or viewer) or proxy mode reads the
    API. With open access, a request without an API token gets `401 {"error":"token required"}` on both addresses.
19. **API tokens (W-053).** Up to 5 named API tokens with the scope `ha` (only `/api/v1/ha`) or `full` (both). An `ha`
    API token gets `403 {"error":"the API token permits only /api/v1/ha"}` from `/api/v1/status`. The API token of the
    version before is the API token "API token" with the scope `full`.
20. **Times (W-049).** Every time is UTC without fractions of a second (`2026-10-11T15:29:17Z`). `servers[].last_contact` and
    `devices[].last_seen` had the local offset and fractions of a second. A time that is not known is `null` and the key
    is always in the answer (before, `last_contact`, `cert_expires`, `last_seen` and `notifications.since` were missing).
21. **HA status values (W-049).** `up to date` → `up_to_date`, `watch error` → `watch_error`; `unknown` → `unreachable`
    (the server is down), `certificate_changed` (a changed certificate) or `not_contacted` (no full check after the start).
    Unchanged: `syncing`, `scanning`, `error`, `paused`, `disabled`.
22. **HA status error (W-054).** `error` only while an H4 finding with the severity ERROR is open for the server (snoozed
    or not). For failed items without H4, the status is `syncing`. `folders_error` did not change.
23. **New in /api/v1/status:** `servers[].site`, `notifications.next_try`, `findings[].snooze_until`,
    `findings[].snooze_reason`, `links[]`, `site_links[]`. `servers[]` and `devices[]` are `[]` when empty (were `null`).
24. **New in /api/v1/ha (W-052, W-057):** at the top `findings_open`, `findings_urgent`, `findings_error`,
    `findings_warn`, `findings_info`, `notifications_failing`, `notifications_failing_since`, `links`, `site_links`; for
    each server `site`, `last_contact`, `findings_open`, `findings_urgent`.

## README lines (STE, for the Docs stage)

JSON status API, access and API tokens:

- Each program that reads the API needs an API token or a logged-in session. With open access, a person without a login
  sees the dashboard pages, but the API answers `401`. In proxy mode, the reverse proxy also controls access to the API.
- Make the API tokens in Settings → API. There are at most 5 API tokens. Each API token has a name and a scope.
- The scope Home Assistant permits only `GET /api/v1/ha`. That answer has the names, states and numbers of the servers,
  without device IDs, addresses and folder paths. The scope Full also permits `GET /api/v1/status`.
- Give each program its own API token. Then you can replace or revoke one API token, and the other programs continue to
  work.
- syncwatch shows the value of a new API token one time. syncwatch keeps only the SHA-256 hash of the value.
- Settings → API shows the time of the last use of each API token. The time is at most 1 minute late. A request that the
  scope refuses is also a use.
- An ha API token gets `403` with `{"error":"the API token permits only /api/v1/ha"}` from `/api/v1/status`. An unknown
  API token gets `401`.
- After the update, the API token of the version before is the API token with the name "API token" and the scope Full.
  It continues to work.
- An imported `api.token` is the new value of the API token with the name "API token". Its scope does not change. If that
  API token does not exist, syncwatch adds it with the scope Full. With 5 API tokens, syncwatch refuses the import.
- Each time in the API is UTC in the form `2026-10-11T15:29:17Z`, without fractions of a second. A time that syncwatch
  does not know is `null`. The key is always in the answer. (This replaces "The time fields are UTC (RFC 3339).")

Home Assistant:

- The status of a server has one of these values: `up_to_date`, `syncing`, `scanning`, `watch_error`, `error`, `paused`,
  `unreachable`, `certificate_changed`, `not_contacted` or `disabled`. The values have no spaces and do not change with
  the texts of the dashboard.
- With `not_contacted`, syncwatch did not finish a full check of the server after its start. With `unreachable`,
  syncwatch cannot reach the server. Thus an automation on `unreachable` does not start after a restart of syncwatch.
- The status is `error` only while an H4 finding with the severity ERROR is open for the server, also when it is
  snoozed. Syncthing repairs many failed items itself, and H4 waits for that. Until then, the status shows the folder as
  `syncing`. `folders_error` always counts the folders with an error. (This replaces "The status of a server can show
  `syncing` or `error` for a short time without a finding.")
- If you set H4 to off in Settings → Checks, the status never shows `error`.
- `findings_open` and `findings_urgent` count the open findings that are not snoozed or ignored. For a server, they count
  its findings and the findings that relate to it, for example a PC that the server knows.
- `links` and `site_links` show if the servers and the sites are connected. Use them to see a cut VPN.
- The example (`examples/home-assistant.yaml`) can read `findings_urgent` from `/api/v1/ha`. It then needs no second
  request to `/api/v1/status`, and an API token with the scope Home Assistant is sufficient.

What you must do after the update:

- Scripts that read the API with open access need an API token now.
- Home Assistant: change each template and automation that compares the status with `up to date`, `watch error` or
  `unknown`. Use `up_to_date`, `watch_error`, `unreachable` and `not_contacted`.
- Optional: add an API token with the scope Home Assistant, and give it to Home Assistant. Then Home Assistant cannot read
  device IDs, addresses and paths.

The steps "To replace the API token" of the README become: 1. In syncwatch, open Settings → API and select **Replace** at
the API token of Home Assistant. syncwatch refuses the old value immediately. (Steps 2 and 3 stay.)
