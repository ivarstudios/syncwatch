## 1. W-016: a refused save of the Checks form discarded every other typed value

- Root cause: `handleChecksSave` and `save()` answered a parse or `Validate` error with a flash cookie and a 303 to
  `/settings#checks`. The GET built the page from the stored configuration, so all typed values went back, and the flash
  showed at the top of `<main>`, far above the Checks card. Collector and Notifications did the same.
- Changed (`settings.go`, `settings.html`): a refused save of the Checks, Collector or Notifications form answers with the
  settings page itself, HTTP 422 (`refuse()`). The page is built from the stored configuration with its revision (`Rev` =
  `configRev(old)`, so the corrected save is not refused as stale). The inputs of that form show the posted text
  (`Form` map, `checkRow` for the checks table), also text that cannot go into the configuration ("3 days"). The error shows
  above the Save button of that form (`<p id="checks-error" class="flash err" role="alert" tabindex="-1" autofocus>`), not in
  the flash at the top. The bad inputs get `aria-invalid="true"` and `aria-describedby`, and their label (or the row of the
  check) gets the existing class `c-err` (red). `save()` returns the error and writes nothing then. `badInputs()` reads the
  YAML keys that `config.FieldLabel` puts in the validation message ("(thresholds.pc_offline)") to mark the inputs. The
  parse errors of the duration fields come in the order of the form (they came in map order). `render()` (server.go) is
  unchanged: the message goes in the page data.
- User-visible: after "Save checks" with `pc_offline` 5s, the browser shows the Checks section with 30m, 12h and 5s still
  typed, the H7 label red and the message above the button; the error box has the focus, so the browser scrolls to it
  (s25: `scrollY` 2031, error at 429 px and the field at 273 px of a 900 px window; `shots\w016-thr-5s-*.png`,
  `w016-thr-5s-viewport.png`). The address bar shows `/settings/checks`; a reload asks to send the form again.
  A typed webhook URL is not shown again; the message then ends with "Type the Discord webhook URL again."
- Tests: `TestRefusedChecksSaveKeepsTypedValues` (the plan's case: 30m, 12h, 5s; the configuration does not change; the
  revision of the answer accepts the corrected save), `TestRefusedChecksSaveKeepsTextThatIsNotADuration`,
  `TestRefusedCollectorAndNotificationSavesKeepTypedValues`.
- DECISION: the form keeps `action="/settings/checks"` (no fragment), so the drivers of the personas still find it; the
  `autofocus` on the error box scrolls to it. A refused save of the Servers, Access, Structure and import forms still
  redirects with a flash (not in the plan; `web_test.go` `TestSettingsForms` asserts the redirect for a bad structure
  pattern, and the Servers form has secrets and many refusal paths).
- DECISION: a `SaveConfig` error of the Notifications form after the webhook is stored (a database error) still redirects:
  the webhook is already saved then, and "Type the webhook URL again" would be wrong.

## 8. W-026: a tripped login limiter blocked the logged-in administrator's confirmations, with the wrong message

- Root cause: `limitedCheck` counted a password typed to confirm a change in the login bucket of the client address.
  Five wrong logins of other people at the same address (a VPN that masquerades, a reverse proxy, the kit edge) blocked
  the administrator's access and password changes ("Too many failed logins…"), and `confirmed()` returned only false, so
  accept-cert asked for the password that was typed.
- Changed (`settings.go`, `auth.go`): confirmations (accept certificate, remove the pinned certificate, access change,
  import, password change: `confirmed()`, `confirmAdmin()`, `handlePasswordSave` through `limitedCheck`) count in a
  bucket of the session (`confirmKey`: "session <token hash>"; without a session, in proxy mode, "confirm <address>", which
  is separate from the login bucket of the address). The limit is the same: 5 failures in 10 minutes. The failures still
  count for the slowdown of all password checks (30 failures from everywhere). When the limit refuses a confirmation, the
  message says so: "Too many failed tries. Try again in N minutes." (`tooManyTries`, N rounded up from the new
  `limiter.retryAfter`). Logins keep "Too many failed logins. Try again in 10 minutes."
- Live (s25, same sequence as `t_limiter_roles.py` step e): before (base image) accept-cert with the correct password →
  "To accept the new certificate, type the administrator password or this server's API key.", access and password →
  "Too many failed logins. Try again in 10 minutes."; after → "The new certificate is accepted.", "The access settings are
  saved.", "The administrator password is changed."; the session's own 5 wrong confirmations → "Too many failed tries.
  Try again in 10 minutes." (`w026-limiter-before.txt`, `w026-limiter-after.txt`).
- Tests: `TestFailedLoginsDoNotBlockAdminConfirmations` (the script's sequence), `TestAdminConfirmationsAreLimitedBySession`
  (own limit, message, another session and a login at the same address still work), `TestLimiterRetryAfter`. The existing
  limiter tests (`TestPasswordChangeIsRateLimited`, `TestPinChangesNeedConfirmation`, `TestLimiter*`, `TestParallelLoginsAreLimited`,
  `TestViewerLoginKeepsAdminFailures`, `TestLoginRateLimit`) pass unchanged.
- DECISION (fixed in the plan): logins keep r0-e's count for each address, and 5 failures at one address block the logins
  of every role (fixer 8 documents this, W-066).
- DECISION: "tries" instead of the plan's "attempts" (STE word list; the setup page already says "Too many failed tries.").
- Re-opens r0-e item 1 for confirmations only ("confirm fields, the password-change form and the setup token count as
  admin attempts" of the address): the setup token keeps the address bucket (there is no session).
