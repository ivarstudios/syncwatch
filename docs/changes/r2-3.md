## 1. W-045 (lead): a daily baseline scan when the last one was fast

**Today.** Synced project folders are walked only at the baseline scan (`baseline_interval`, 7 days) or from Syncthing's
events. On some NAS storage the file watcher is blind without an error (data-steward: S3 after 38 minutes).

**What changed.** `internal/collector/structure.go`: `maybeScan` starts a baseline scan when the last one is
`baselineEvery(cfg)` ago: `min(baseline_interval, 24h)` when the last completed baseline scan of the collector took less
than 10 seconds (`fastBaseline`), else `baseline_interval`. `scan` keeps the duration of each completed baseline scan
(`noteBaseline`: `Collector.baseTook`, `baseKnown`, under `scanMu`). The first scan after a start (or a restart of the
collector after a change of the collector settings) is a baseline scan as before. The choice is logged at INFO once for
each change:

- `baseline scan every day: the last one took less than 10 seconds` (`took=5ms`)
- `baseline scan every 7 days: the last one took 10 seconds or more` (the interval in words; `took=14.2s`)

**DECISION:** until a baseline scan completed (none since the start, or the first one was cancelled), the interval is
`baseline_interval`. A cancelled baseline scan (the session ended, the server went down) does not change the duration.
As before, a started baseline scan counts as the last one: a baseline scan that a lost server cancels comes again only
after the interval (limit, not changed).
**DECISION:** no log line while `baseline_interval` is 1 day or less: then the duration changes nothing (`2h` stays
`2h`). The first choice after a start is logged too (it is a change from "not known").

**User-visible.** With the default `baseline_interval: 7d` and a baseline scan under 10 seconds (the ORION data: less than
1 second for each NAS), syncwatch walks every synced project folder each day. A project folder copied into another
project folder is found in less than 1 day, also when Syncthing reports no change. The log names the interval.

**Tests.** `TestBaselineEvery` (fast and 7 days → 24 h; slow → 7 days; exactly 10 s → 7 days; not known → 7 days; 2 hours
stays 2 hours, fast or slow; 30 days and fast → 24 h), `TestMaybeScanUsesDailyBaseline` (the scan that `maybeScan` starts:
7 days, fast, 25 hours ago → baseline; fast, 23 hours ago → regular; slow, 25 hours ago → regular; slow, 7 days ago →
baseline; 2 hours, 3 hours ago → baseline, 1 hour ago → regular), `TestBaselineChoiceLogged` (the lines once for each
change; none for `1d`).

**Live (s23).** Settings → Collector: `baseline_interval` 1h → 7d, `structure_interval` 1m (`14-collector-form.txt`). The
collectors restarted; the first scan of each server was a baseline scan (`listings=34` on AKKA, 29 on SOL) and logged
`baseline scan every day: the last one took less than 10 seconds` (took 5 ms and 225 ms); after `envctl sw s23 syncwatch
restart` the same; then a regular scan each minute (`baseline=false`, 4 and 3 listings) with no further choice line
(`16-baseline-log.txt`). With `baseline_interval: 1h` (the kit's value, before the change) no choice line was logged.

## 2. W-047.listener: the state of each NAS's relay listener

**What changed.**
- `internal/stclient/types.go`: `SystemStatus.ConnectionServiceStatus map[string]ListenerStatus`
  (`json:"connectionServiceStatus"`), `type ListenerStatus struct { Error *string; LANAddresses, WANAddresses []string }`
  (C9).
- `internal/collector/listeners.go` (new): `relayListeners(prev, status, now)` keeps the listeners whose scheme is `relay`
  or starts with `dynamic+`, with the URI without its query (`relayURI`); `Connected` = 1 or more WAN addresses and no
  error; `Error` = Syncthing's text; `Since` stays as before while `Connected` stays, a new listener or a change gets
  `now`. `setRelayListeners` writes `Server.RelayListeners` (C3) at the session start and at each full check (both read
  `/rest/system/status`), and `sampleListeners` once each minute in the traffic loop while the server is up and loaded
  (1 more request per minute; a failure is left to the session).

**Answer form, verified on kit slot s23** (`01-…` to `03-…`, `08-…`): Syncthing 2.1.6 (AKKA) and 2.1.5 (SOL after
`envctl set-version`) have the same form:

```json
"connectionServiceStatus": {
  "relay://10.123.1.60:22067/?id=JYSLS6U-…-2QBLQAC": {"error": null, "lanAddresses": ["relay://…"], "wanAddresses": ["relay://…"]},
  "tcp://0.0.0.0:22000": {"error": null, "lanAddresses": ["tcp://0.0.0.0:22000", "tcp://10.123.1.10:22000"], "wanAddresses": ["tcp://0.0.0.0:0", "tcp://0.0.0.0:22000"]}
}
```

After `envctl stop s23 relay` the relay listener keeps its WAN address and gets an error:
`"error": "dial tcp 10.123.1.60:22067: connect: connection refused"` (later `connect: no route to host`). Thus the rule
"a WAN address and no error" is needed; the WAN address alone would say "connected". After `envctl start s23 relay`
Syncthing connects again after 35 seconds to 2 minutes (its own retry). The kit's private relay has no `token=` in the
address; a relay with a token has it in the same query, which syncwatch removes.

**DECISION:** the URI also loses a fragment and a lone trailing `/` (`relay://10.123.1.60:22067/?id=…` →
`relay://10.123.1.60:22067`, the form of the contract's example). An address that is not a URL is cut at `?` and `#`.
The listeners are ordered by URI.

**Tests.** `TestRelayListeners` (the kit's relay listener connected; a `dynamic+https` one without a relay; TCP and QUIC
ignored; the stopped relay: error, WAN address kept → not connected, new `Since`; the unchanged listener keeps `Since`;
both connected again; no `token` and no `?` in any URI), `TestRelayURI`, `TestRelayListenersSampled` (the collector: the
listener after the first full check; the relay stops → the minute's sample shows it without a new session or full
check), `TestSystemStatusListeners` (stclient parses the answer of 2.1.6).

**Live (s23).** The collector of this branch against the gate of AKKA (`zz_live_r23_test.go`, a harness with the build
tag `livecheck`, not committed; snapshots every 10 seconds): relay stopped at 19:23:11 → the minute's sample at 19:23:27
`Connected false`, `Since 19:23:27`, error "connection refused"; relay started at 19:24:10 → the sample at 19:25:27
`Connected true`, `Since 19:25:27` (`13-relay-summary.txt`, `13-harness-relay-cycle.jsonl`). H12 itself is fixer 2's.

## 3. W-058.fetch: the files that a PC still needs, through the client and the gate

**What changed.**
- `internal/stclient`: endpoint `/rest/db/remoteneed` in the allowlist; `RemoteNeed(ctx, folder, device, perPage)` sends
  `folder`, `device`, `page=1`, `perpage`; types `RemoteNeed{Files, Page, PerPage}` and `NeedFile{Name, Size, Deleted}`
  (C9). New helper `GateRefusedEndpoint(err)`: a 404 whose body starts with `syncwatch gate: endpoint not permitted`.
- `internal/gate`: the gate permits the endpoint (its allowlist is the client's). `checkQuery`: only `folder`, `device`,
  `page`, `perpage`, each 1 time (as before for all endpoints); `folder` necessary and not empty; `device` a complete
  device ID (`^[A-Z2-7]{7}(-[A-Z2-7]{7}){7}$`); `perpage` necessary, 1 to 100; `page` optional, 1 to 1000. No cleaner.
  The answers: `syncwatch gate: query not permitted: the parameter folder is necessary`, `…: the parameter device must
  be a complete device ID`, `…: the parameter perpage must be between 1 and 100`, `…: the parameter page must be between
  1 and 1000`.
- `internal/collector/need.go` (new) and `fullCheck`: for each folder that is not paused and each device with
  `NeedItems > 0` that is connected (`/rest/system/connections` of the same check), the completion request reads
  `RemoteNeed(folder, device, 20)` in the same slot of the throttle. `NeedList{Names: the first 20 names, Items: the need
  items of the completion, At: the time of the completion read}`. The check replaces `Server.NeedLists` at its end (C3).
  A failure costs only the names: the check goes on, the folder gets no error. An older gate's 404: one INFO line
  `the gate does not permit /rest/db/remoteneed: update the gate to see the needed files in H5`, and no more requests in
  the session. Other errors: DEBUG `cannot read the files that a device needs` (folder, short device ID, error).

**Answer form, verified on kit slot s23** (`04-…`, `06-…`, `07-…`, `09-…`, `11-…`): Syncthing 2.1.6 and 2.1.5 answer the
same: `{"files": [ <file info> … ], "page": 1, "perpage": 20}`; each file info has `name`, `size`, `deleted`, `type`
(`FILE_INFO_TYPE_FILE`, `FILE_INFO_TYPE_DIRECTORY`), `modified`, `modifiedBy`, `version`, `platform` and more. Directories
are in the list and count in `needItems` (1 new directory with 3 files = 4 need items). An unknown folder: 404
`no such folder`; a device ID that is not valid: Syncthing answers 500 (the gate refuses it with 400 first); a device that
does not share the folder: Syncthing lists the whole folder (the collector asks only for the devices of the folder); a page
after the end: `"files": []`. Through the r1 gate (`dev` image): 404 `syncwatch gate: endpoint not permitted`; through the
gate of this branch: 200 with the names, and the refusals above (`11-remoteneed-new-gate.txt`).

**DECISION:** `Names` has every entry of the page in Syncthing's order, also directories and deletions (they count in
`Items`). The names are raw paths from Syncthing: they can have control characters, Discord mentions or HTML (the
hostile names of r1, `the test kit`). The rules, the notifier
and the dashboard must escape them like other Syncthing texts (fixers 2, 4, 6). The collector does not log them.
**DECISION:** after the 404 of an older gate, the collector asks no more in the session (the gate logs each refusal):
one INFO line for each session. A new session (for example after an update and a restart of the gate) asks again.
**DECISION:** `At` is the time of the completion read of the same check (a few milliseconds before the list), so a list
and its completion have the same time; a later `FolderCompletion` event makes the list older than the completion.

**Tests.** stclient `TestRemoteNeed` (the query, the 2.1.6 answer form), `TestGateRefusedEndpoint`, the allowlist tests
(`TestOnlyAllowlistedGETs`, `TestAllowlistIsExactly`); gate `TestGateQueryAllowlist` (accepted: page 1 and perpage 20,

## 5. W-021.persist: the first-seen time and the last local change survive a restart

**What changed.** `internal/collector/activity.go` (new) and `fullCheck`: at each full check the local changes that wait
are written first (`flushLocalChanges(true)`), then `NoteFoldersSeen(server, all folder IDs, now)` and
`FolderActivity(server)`; `Folder.FirstSeen` comes from the store, `LastLocalChange` is the later of the store and the
memory. On `LocalChangeDetected` the memory changes as before (only when the event is newer); the store gets the newest
time at once when the folder had no write in the last minute, else the folder waits (`localDue`). What waits is written
after a later long-poll when its minute is over, at the next full check, and when the collector stops (`Run` writes it
before it returns; the application closes the store only after the collectors). A store error: a WARN line, the full
check goes on (`FirstSeen` then keeps the memory value).

**DECISION:** `NoteFoldersSeen` comes before `FolderActivity` (the plan has the other order): 1 read gives both times,
with the same result. **DECISION:** besides "the next full check writes what is left" (plan), a later long-poll and the
stop of the collector write it too; with full checks every 4 hours the store would otherwise lag up to 4 hours. A failed
write stays due and is tried again after a minute. **Limit (not changed, foundation note):** the rows of folders and
servers that are gone stay; a folder ID that comes back later gets its old first-seen time.

**User-visible.** None directly: C1 (fixer 2) uses `FirstSeen` and `LastLocalChange`, also after a restart.

**Tests.** `TestFolderActivitySurvivesRestart` (a new manager and collector on the same store, without the old events:
`FirstSeen` of each folder and `LastLocalChange` of p-alpha as before, none for p-beta), `TestLocalChangeBurstWritesFewRows`
(1,000 `LocalChangeDetected` in 1 second: 1 write with the first time; the next full check writes the newest (2 writes);
1 more change within the minute waits and the stop writes it (3 writes)), `TestLocalChangeTimeTracked` (unchanged, still
passes).

**Live (s23).** `folder_activity` rows from a copy of the store (`activity_rows.sh`, the copy is deleted): after the image
change every folder of AKKA and SOL has `first_seen`; a file written on AKKA in LIVE-FJORD-1SOURCE at 19:24:37 gives
`last_local_change 17:24:38.471Z` (UTC) within 4 seconds; after `envctl sw s23 syncwatch restart` the rows are the same
(`15-folder-activity.txt`).

## 6. W-035.hook: tell the application about a new pinned certificate

**What changed.** `newCollector` has a new last parameter `onPin func(serverID, fingerprint string, renewal bool)`;
`Manager.Sync` passes `Manager.OnPin` (F8). The client's `OnPin` function reads the stored pin, saves the new one
(`SetPin`, as before) and then calls `onPin(serverID, fingerprint, renewal)` with `renewal` = a pin was stored before (a
CA-signed renewal), false = the first contact. New package variable `rootCAs` (nil = the system pool, as before) for the
test CA.

**DECISION:** `onPin` runs in its own goroutine. The client calls its `OnPin` inside the TLS handshake while it holds its
lock: a hook that asks the client (for example `LastCert`) or waits on the notifier would block or stop the handshake.
The doc comment of `Manager.OnPin` says it. **DECISION:** no call when the stored pin is already this fingerprint. When
the stored pin cannot be read: a WARN line and `renewal` false (a notice is better than none).

**Tests.** `TestOnPinFirstUseAndRenewal`: the first contact → `OnPin("akka", <fingerprint>, false)` and the pin is stored;
the pinned certificate again → no call; a certificate from a certificate authority (the test server's certificate as the
CA through `rootCAs`) replaces an older pin → `OnPin("akka", <fingerprint>, true)`, stored, `Cert.CASigned`.

**Live.** The harness (a new store) logged `OnPin called server=akka fingerprint=39990d48… renewal=false` at the first
contact with the gate of AKKA (`10-harness-old-gate.jsonl.log`, `12-harness-new-gate-relay.jsonl.log`). The settings
notice is fixer 8's. Steps for the integrator after the merge of fixer 8: Settings → Servers → SOL → remove the pinned
certificate (with the administrator password); at the next new connection to SOL (a new session, for example `envctl sw
SLOT syncwatch restart` or a restart of SOL's gate) the fake Discord gets "Server SOL: certificate pinned".
