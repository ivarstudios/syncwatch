## W-051 (lead): security notices are kept; a webhook only for settings notices

**What changed (`notices.go`, `notifier.go`, `discord.go`).**

- `pendingNotice` is now stored: the setting `notify.kept_notices` (JSON list: key, title, summary, security, the time of
  the change, the give-up time). The notifier reads it at its first use (the first tick, `Delivery()` or a new kept
  notice: "kept settings notices loaded" INFO) and writes it at each change. At most 50 notices: the oldest notice that is
  not about security goes first, then the oldest security notice.
- First send of a notice (`notice`): sent → one line "✔ sent" (as before). Failed:
  - `Security: true` and HTTP 400 (the message is not valid): deleted, one WARN "settings notice discarded, Discord
    refused it", notification log "discarded: <error>".
  - `Security: true`, any other failure (401, 403, 404, 5xx, timeout, a webhook that cannot be used or decrypted): kept
    with no time limit, one WARN "settings notice kept until a channel accepts it", notification log "kept until a channel
    accepts it: <error>".
  - `Security: false`: the rules of r1, unchanged: refused (4xx) by the channels that are still configured → deleted;
    any other failure → kept for 1 day (notification log "kept for 1 day: <error>").
  - No webhook at all: not kept (as before), but the notification log now has a line "No Discord webhook is configured."
- Retries (`retryNotices`, `retryOwnNotices`): oldest first, to the channels configured at the retry, one try for each
  tick and channel (they stop at the first failure). A retry adds no line to the notification log until the notice is
  sent ("✔ sent") or deleted ("discarded: …", "discarded after 1 day of send failures", "discarded: more than 50 settings
  notices wait for a channel"). A security notice is deleted on a retry only by HTTP 400; another notice by any 4xx, as
  in r1, and a day after the change.
- `Delivery.NoticesKept` = the number of kept notices.
- Webhook for settings notices: `defaultNoticeSenders` builds a `Discord` sender with the channel name `discord-notices`
  (new field `Discord.Channel`) and no role ID (never a mention) from `store.SecretNoticesWebhook`; a secret that cannot
  be decrypted is a `brokenChannel` named `discord-notices` with the error "syncwatch cannot decrypt the Discord webhook
  for settings notices: check the secret key" (the ERROR log line comes once, not at each tick). `Notice` and
  `NoticeLater` send to it when it is set, else to the channel of the findings (`noticeTargets`). Its result never goes
  into `Delivery` (that is the channel of the findings). It has its own back-off (`ownChannel`, the same 1, 2, 4, 5 … /
  … 30 minutes as `fail`), thus a failing notices webhook does not hold up the urgent messages. `ChannelsChanged` also
  resets it.
- Fallback (DECISION of the plan): a kept security notice also goes to the channel of the findings when the webhook for
  settings notices fails for more than 1 hour. The first channel that accepts it ends the wait. The same holds for the
  first send of a new security notice while that webhook already fails for more than 1 hour.
- `SendNoticesTest` sends "syncwatch test notice" ("Settings notices from syncwatch reach this channel. They mention no
  role.", grey, kind `test`) to the webhook for settings notices; without one it returns "No Discord webhook for settings
  notices is configured."; a success ends the back-off of that webhook and wakes the notifier (the kept notices go out).

**User-visible.** A changed API key, certificate, password or webhook during a Discord outage or with a deleted webhook
is announced when a channel works again, also after a restart (r1: deleted after one retry, OC-03). With the optional
second webhook, settings notices go to their own channel without the role mention. Settings → Recent notifications has one
line for each decision about a settings notice.

## README lines (Docs stage)

Notifications (README "Notifications", the bullets of the message kinds):

- Settings notice: syncwatch keeps a settings notice about security until a channel accepts it, also through a restart.
  These are the changes of API keys, gate tokens, pinned certificates, passwords, the access settings, the webhooks and
  API tokens, and imports. syncwatch deletes such a settings notice only when Discord refuses the message itself (HTTP
  400). syncwatch tries other settings notices again for 1 day, and deletes them when Discord refuses the webhook (HTTP
  401, 403 or 404).
- Optional: a second Discord webhook only for settings notices (`notifications.discord_notices_webhook`). The settings
  notices then go to its channel, without the role mention, and the first webhook gets only the messages about findings.
  When the webhook for settings notices fails for more than 1 hour, syncwatch also sends each settings notice about
  security to the first webhook.
- The list of recent notifications in Settings has a line for each settings notice: sent, kept with the error, or
  deleted.
- Repeat urgent messages every (`notifications.repeat_urgent`) is off by default. When it is on, syncwatch sends the
  urgent message again with the role mention while an urgent ERROR finding of a server stays open. syncwatch does not
  repeat a finding that is snoozed, ignored or about more than 1 server. syncwatch sends no repeat in the quiet hours.
  It sends a repeat that falls due in the quiet hours when they end.
- The daily reminder does not list a finding with an urgent message or a repeat in the hour before the reminder time.
- Urgent message (replaces "Findings that open in the same cycle go into one message"): syncwatch waits 10 seconds after
  the first finding of an urgent message falls due. Urgent findings that fall due in these 10 seconds go into the same
  message.
- Resolved message: a resolved message tells what is correct again, for example "Servers AKKA and SOL are connected
  again". It also gives the time from the start of the fault to its end, with the clock times: "the fault lasted 7
  minutes, 21:10–21:17". When the fault ended while syncwatch did not run, the message gives that time instead of the
  end.
- After a stop, the next message about findings gives the time when syncwatch did not run: "syncwatch did not run from
  21:04 to 21:24."
- Urgent messages, repeats and the daily reminder show the first advice of a finding under its line. The advice is the
  first row of Possible causes, What to check or What to do. Thus the team at the other location can read the possible
  cause also when the VPN is down and the dashboard does not open.
- The same finding on more than 1 server is 1 line in each message: "… (also on SOL)". The views of 1 PC from AKKA and
  SOL are 1 line: "… (also seen from SOL)". The dashboard and the API keep these findings separate.
