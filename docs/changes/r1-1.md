## 1. W-009, client part: a gate refusal gets the API key hint

**Root cause.** `StatusError.Error()` (`internal/stclient/client.go:126-131` at `2a1a933`) returned `<endpoint>: HTTP <code> (check the API key)` for every 401 and 403 and dropped the body. The gate answers with its own text (`syncwatch gate: gate token missing or not correct`, `syncwatch gate: directory not in a permitted browse root`), but that text never reached the server tile, the H1 message, Discord or the share line. A wrong gate token, a share outside the browse roots of the gate and (behind a gate) a key that Syncthing refused all showed the same hint. This also contradicted r0-b item 1 ("the collector's `shortErr` shows that as the share's error").

**What changed** (`internal/stclient/client.go`). When `Body` starts with `syncwatch gate:`, `Error()` returns `<endpoint>: HTTP <code>: <first line of the body, at most 200 bytes>`. When that text has the browse-root reason, it adds ` (add the directory to SYNCWATCH_GATE_BROWSE_ROOTS on the gate)`. A 401 or 403 without a gate body keeps the old text exactly (contract C2). Any other answer without a gate body keeps `<endpoint>: HTTP <code> <body>` (`collector_test.go:1026`). `Code` and `Body` do not change, thus `perFolder()`, `serverLevel()` and `paused404()` in the collector work as before.

**User-visible** (H1 message, server tile, share line, Discord):

| Case | Before | After |
|---|---|---|
| wrong gate token in Settings → Servers | `/rest/system/status: HTTP 403 (check the API key)` | `/rest/system/status: HTTP 403: syncwatch gate: gate token missing or not correct` |
| share outside the browse roots of the gate | `/rest/system/browse: HTTP 403 (check the API key)` | `/rest/system/browse: HTTP 403: syncwatch gate: directory not in a permitted browse root (add the directory to SYNCWATCH_GATE_BROWSE_ROOTS on the gate)` |
| API key of Syncthing changed behind a running gate | `/rest/system/status: HTTP 403 (check the API key)` | `/rest/system/status: HTTP 502: syncwatch gate: Syncthing refused the API key of the gate. Restart the gate with the current API key` (item 2) |
| wrong API key, no gate | `/rest/system/status: HTTP 403 (check the API key)` | unchanged |
| other gate answers | `… HTTP 502 syncwatch gate: Syncthing unreachable: …` | `… HTTP 502: syncwatch gate: Syncthing unreachable: …` (a colon after the code) |

The H1 message itself ("Server SOL is unreachable: …") is fixer 3's (W-009, H1 text).

**Tests.** `TestStatusErrorTexts` (`internal/stclient/client_test.go`): 8 cases (401 and 403 without a gate body, the gate token, the browse root, the key refusal, a body with 2 lines, a body over 200 bytes, a 500 without a gate body); each text with 401 or 403 matches `HTTP 40[13]\b` and the others do not. `TestClientThroughGateErrors` (`internal/gate/gate_test.go`): syncwatch's client through a real gate for the 3 gate cases. This test also keeps the browse-root reason of the gate and the match in the client the same.

**Live** (kit s21): `kit-wrong-token-before.txt` / `kit-wrong-token.txt` (H1 and the Discord message with the gate text) and `kit-browse-root-before.txt` / `kit-browse-root.txt`, `shots-browse-root/root-phone.png` (the share line on the Overview, phone width).

- DECISION: H1 stays the check for 401 and 403 (README Checks table, `collector_test.go:1027`). Only the texts change. Fixer 3 changes the H1 message and finds a refused key or gate token with `HTTP 40[13]\b` (contract C2).
- DECISION: the gate text stays in the error with its `syncwatch gate:` prefix, thus the reader sees which side refused. The browse-root instruction is in parentheses, in the form of the existing `(check the API key)`.

## 2. W-009, gate part: Syncthing refuses the API key of the gate, and the gate is silent

**Root cause.** The gate reads the API key of Syncthing one time, at start (`internal/app/gate.go:46`, `gateSyncthingKey`), also from `config.xml`. After a change of the key in Syncthing, Syncthing refused each request, and `ServeHTTP` (`internal/gate/gate.go:338-341` at `2a1a933`) passed that 403 on without a log line. syncwatch then said "check the API key", which pointed to the gate token in syncwatch, and that token was correct (DD-8, map 01 hunch 4).

**What changed** (`internal/gate/gate.go`).
- An answer 401 or 403 from Syncthing (not for `/rest/noauth/health`, which gets no API key) goes to `keyRefused()`: the gate answers **502** with the body `syncwatch gate: Syncthing refused the API key of the gate. Restart the gate with the current API key` (101 bytes) and logs at WARN `Syncthing refused the API key of the gate: restart the gate with the current API key` with `status`, `path` and `count`, at most one time each minute.
- The counting of `deny()` moved into `due(key)`. `deny()` uses it as before (client address and reason). The key refusal uses one key for the whole gate, because the cause is the configuration of the gate, not a client.
- The own folder-list read of the gate (`getJSON`, for browse requests) wraps a 401 or 403 in `errKeyRefused`. `upstreamError()` turns it into the same 502 body, and the existing warning `cannot read the folder list of Syncthing, browse requests need it` has `err=/rest/system/status: HTTP 403: Syncthing refused the API key of the gate`.
- A wrong gate token stays the 403 of the gate itself. Thus syncwatch can tell a wrong gate token (403, "refuses the API key or the gate token" in fixer 3's H1) from a key that the gate must read again (502).

**User-visible.** See the table in item 1. The gate log has one warning each minute while Syncthing refuses the key.

**Tests.** `TestGateSyncthingRefusesKey`: a fake Syncthing that refuses the key of the gate; status, version, events, config/folders, db/status, metrics and browse each get the 502 with the exact body (under 150 bytes); health still works; a wrong gate token still gets the 403 of the gate; 1 log line in the first minute with `status=403`, then 1 more line with `count=5`.

**Live** (native, DD-8 cannot be done in the kit because its Syncthing sets `STGUIAPIKEY`): `native-dd8-before.txt` (gate from `2a1a933`: after `PATCH /rest/config/gui apiKey`, every request gets Syncthing's `403 CSRF Error`, no log line) and `native-dd8-after.txt` (502 with the instruction, 1 WARN line; then a restarted gate reads the new key from `config.xml` and gets 200). Note: this test Syncthing has no GUI user, thus it answers `/metrics` with any key (200 in both runs); with a GUI password, `/metrics` also refuses the key.

- DECISION: the gate does not read `config.xml` again after an upstream 401 or 403 (optional in the plan). The README contract for fixer 8 says "the gate reads the API key only at start; restart the gate after a change of the key". A key that can change at run time is shared state for each request, and a change of the Syncthing API key is a rare manual step. The 502 text and the log line give the instruction. This can be added later in `internal/app/gate.go` with a callback in `gate.Options`.
- DECISION: 502 (not 401 or 403) for a key that Syncthing refused, as the plan says. H1 thus keeps "is unreachable" for this case (no `HTTP 401`/`HTTP 403` in the text), and the message has the instruction for the gate.

## 3. W-028: the gate forwards an error answer that it did not clean

**Root cause.** `if clean == nil || resp.StatusCode/100 != 2 { io.Copy(w, …) }` (`internal/gate/gate.go:338` at `2a1a933`, G-F1, unchanged since 78ef2d8). The cleaners ran only for 2xx. A process that answers on the loopback address of Syncthing with a 500 and a `ConfigSaved` payload got the GUI API key and the password hash through the gate (dynsec-gate evidence 15).

**What changed** (`internal/gate/gate.go`, response path). An answer that is not 2xx on a path with a cleaner (`/rest/events`, `/rest/config/folders`) gets the same status and the fixed body `syncwatch gate: Syncthing answered HTTP <code>`. On the other paths the gate forwards the status and at most 4 KiB of the body (`maxErrBody`; the client keeps 200 bytes). 2xx answers do not change. A 401 or 403 goes to item 2 first.

What the collector reads (checked, read-only): `perFolder()` and `serverLevel()` use only the status code; `paused404()` reads 404 with "paused" in the body on `db/status` and `db/completion`, which have no cleaner, thus the body still arrives; `shortErr()` uses `Error()`.

**User-visible.** An error from Syncthing on the event stream or the folder configuration shows as `/rest/events: HTTP 500: syncwatch gate: Syncthing answered HTTP 500`, not with the text of Syncthing. Other endpoints show the text of Syncthing as before.

**Tests.** `TestGateDoesNotForwardUncleanedErrors`: events (500 with a `ConfigSaved` payload) and config/folders (503 with an encryption password) give the fixed body and no secret; db/status 404 `folder is paused` is forwarded, and syncwatch's client still gets `Code` 404 and `Body` `folder is paused`; a 100 KiB error body is cut to 4096 bytes.

**Live** (native, fake Syncthing on `127.0.0.1:23187`): `native-w028-before.txt` (the API key, the hash and the encryption password in the answers, a 100 KiB error body) and `native-w028-after.txt` (fixed bodies, no secret, 404 `folder is paused` forwarded, 4096 bytes).

## 4. W-029: no limit on parallel requests at the gate

**Root cause.** r0-b limited the event mask and the long-poll timeout (G-F3), but not the number of parallel requests. A token holder could hold 200 event long-polls (Syncthing goroutines 238 → 637 in security-reverify).

**What changed** (`internal/gate/gate.go`). After the token check, `acquire()` counts each request for its client address (`clientIP`): at most 4 parallel `/rest/events` (`maxEventsPerClient`) and 64 other parallel requests (`maxOtherPerClient`). A request over the limit gets `429` through `deny()` (one log line each minute for each client and reason, with a count) with the body `syncwatch gate: too many parallel long-polls` or `syncwatch gate: too many parallel requests`. `release()` runs when the request ends and removes the entry of a client without requests. A request without the correct gate token is refused before the count.

Sizing: syncwatch holds 1 long-poll for each server. The full check and the structure scan each send up to `collector.concurrency` (at most 16) parallel requests, plus the traffic sample and a refresh: at most 34.

**User-visible.** None for syncwatch. A client that sends more parallel requests gets 429.

**Tests.** `TestGateLimitsParallelRequests`: 4 held long-polls, the 5th gets 429 with the body; a status request still passes; 64 held version requests, the 65th gets 429; a request from a different client address passes; after the release all held requests end with 200, a new long-poll passes, no client entry stays; 2 log lines.

**Live.** Native (`native-load-before.txt`, `native-load-after.txt`): 200 parallel long-polls, before 200 × 200 and Syncthing goroutines 38 → 439; after 4 × 200 and 196 × 429, goroutines 39 → 47, 1 log line with `why="too many parallel long-polls"`. Kit s21 (`kit-limits-soak.txt`): syncwatch with `concurrency` 16, a full check each minute and a structure scan each minute through both gates: no 429 and no warning in the gate logs, no 429 in the syncwatch log.

- DECISION: the limits are for each client address, not for each token (all clients have the same gate token). Two syncwatch installations behind one NAT address share the limits: with the default concurrency 3 they need at most 2 × 8 = 16 other requests; with concurrency 16 on both, more than 64 at the same time is possible. The README line says the limits.
- DECISION: a long-poll whose client is gone without a closed connection (a VPN cut) keeps its place until its own deadline (its timeout plus 30 s). 4 places leave room for 3 such long-polls and the new one.
